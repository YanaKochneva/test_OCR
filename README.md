# DocPipe

API-сервис распознавания PDF и сканов с восстановлением текста, таблиц и изображений. Основной движок — Docling + RapidOCR с русской моделью PP-OCRv6. Для перепроверки доступно повторное распознавание фрагментов через GLM-OCR в Ollama.

Экспериментальная замена GLM на локальный Nemotron 3.5 Parse для перепроверки
фрагментов: `configs/nemotron-review.yaml`. Основной OCR остаётся Docling.
Подготовка и сравнение CER: [docs/nemotron-review.md](docs/nemotron-review.md).

Экспериментальная конфигурация — `configs/glm-ocr-review.yaml`. На `doc_img_003`
получен `reference_scoped CER = 0.9262%`: исходный OCR — `1.2957%`,
только корпоративный словарь — `0.9361%`. Эталон используется только для
оценки после распознавания. Установка модели с исправленным завершением,
правила отбора исправлений и ограничения метрики описаны в
[docs/glm-ocr-review.md](docs/glm-ocr-review.md).

## Запуск из notebook

Откройте [process_documents.ipynb](process_documents.ipynb) в Jupyter или VS Code,
задайте файлы или папки в `INPUTS` и выполните ячейки сверху вниз.
Notebook запускает CLI через Python из `.venv` проекта; веб-сервер не требуется.
По умолчанию используется CPU без модельной перепроверки. Через `REVIEW_MODE`
можно выбрать `nemotron` или `glm`, если соответствующие модели подготовлены.
Результаты, журналы, CSV-сводка и ZIP сохраняются в `reports/notebook-runs/`.
Для открытия notebook нужно ядро Python с IPython; зависимости обработки берутся
из окружения проекта и автоматически не устанавливаются.

## Запуск в Docker

Требуются Docker Engine и Docker Compose. Из корня репозитория:

```sh
cp .env.example .env
# Задайте AITUNNEL_API_KEY в .env, если нужна внешняя LLM-проверка.
docker compose --env-file .env -f deploy/docker-compose.yml up --build -d
```

В PowerShell для копирования используйте `Copy-Item .env.example .env`.
По умолчанию включён локальный OCR: `DOCPIPE_OFFLINE=true`,
`DOCPIPE_REVIEW_ENABLED=false`; ключ AITunnel не требуется. Для внешней проверки
явно задайте `DOCPIPE_OFFLINE=false`, `DOCPIPE_REVIEW_ENABLED=true` и ключ.
Проверка API-ключа OCR-сервиса по умолчанию отключена для локального доступа.
В Compose она включается через `DOCPIPE_REQUIRE_API_KEY=true` и
`DOCPIPE_API_KEY` (не менее 32 символов).
После запуска откройте http://localhost:8000 — это форма загрузки документов.
Первая сборка скачивает зависимости и модели; ей нужны интернет и несколько гигабайт свободного места. Модели включены в образ. Сервис использует CPU, работает от непривилегированного пользователя и слушает `127.0.0.1:8000`. Для внешнего доступа настройте reverse proxy с HTTPS.

Документация API: [Swagger UI](http://localhost:8000/docs), [OpenAPI](http://localhost:8000/openapi.json).

## Прямой вызов из внешней системы

Для мультиагентной платформы используйте асинхронный сценарий:
создать задание → опрашивать статус → получить JSON или ZIP.
Контракт интеграции: [docs/async-api.md](docs/async-api.md).

Основной endpoint — **`POST /v1/recognize`**. Передайте один или несколько документов в multipart-поле `files`. Сервис выполнит распознавание и в том же HTTP-ответе вернёт ZIP (`Content-Type: application/zip`). Опрос очереди для этого сценария не нужен.

В конфигурации Docker Compose заголовок `X-API-Key` не требуется. Проверку доступа выполняет внешняя платформа.

```sh
curl --fail-with-body --max-time 660 http://localhost:8000/v1/recognize \
  -F "files=@contract.pdf" \
  -F "files=@invoice.png" \
  -o recognized.zip
```

В PowerShell используйте `curl.exe`. Для системы, работающей в той же Docker-сети, адрес сервиса — `http://docpipe:8000/v1/recognize`.

Пример структуры ответа:

```text
recognized.zip
├── manifest.json
├── document_001/
│   ├── document.json
│   ├── document.md
│   ├── document.html
│   ├── document.docx
│   ├── document-flow.pdf
│   ├── document-positional.pdf
│   ├── images/                 # если документ содержит изображения
│   └── ...                    # отчёты качества и проверки
└── document_002/
    └── ...
```

Папки нумеруются в порядке входных файлов; одинаковые имена исходников не конфликтуют. `document.json` содержит распознанную структуру, текст, таблицы и координаты для последующей машинной обработки. Остальные форматы предназначены для просмотра и редактирования.

```json
{
  "batch_id": "...",
  "status": "completed",
  "documents": [
    {
      "source_filename": "contract.pdf",
      "index": 1,
      "status": "completed",
      "job_id": "...",
      "review_required": false,
      "directory": "document_001"
    }
  ]
}
```

**Всегда проверяйте `manifest.json`.** Если часть документов не распознана, ответ также содержит ZIP и HTTP 200, но `status` равен `partial`. У неудачного документа будут `status: failed`, `http_status` и `error`; папки результатов для него не будет. Заголовок `X-Batch-Status` также содержит `completed` или `partial`. Если не удалось распознать ни одного документа, сервис возвращает HTTP 422 с JSON-ошибкой.

## Настройка и эксплуатация

Настройки задаются переменными `DOCPIPE_`, вложенные поля разделяются `__`. Поля и значения по умолчанию описаны в `config.example.yaml` и `src/docpipe/config.py`. API читает переменные окружения; YAML используется CLI через `--config`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DOCPIPE_API__WORKERS` | 1 | Потоки обработки; один экземпляр OCR выполняется последовательно |
| `DOCPIPE_API__MAX_QUEUE` | 16 | Максимальная очередь ожидания |
| `DOCPIPE_API__MAX_JOBS` | 1000 | Максимум сохранённых заданий |
| `DOCPIPE_API__RESULT_TTL_SECONDS` | 3600 | Срок хранения после завершения |
| `DOCPIPE_LIMITS__MAX_FILE_MB` | 200 | Размер входного файла |
| `DOCPIPE_LIMITS__MAX_PAGES` | 300 | Максимум страниц |
| `DOCPIPE_API__MAX_BATCH_FILES` | 16 | Максимум документов в одном запросе |
| `DOCPIPE_API__MAX_BATCH_MB` | 200 | Общий размер входных файлов запроса |
| `DOCPIPE_API__SYNC_MAX_PAGES` | 300 | Максимум страниц одного документа в прямом API |
| `DOCPIPE_API__SYNC_TIMEOUT_SECONDS` | 600 | Таймаут ожидания синхронного API |

Compose отключает проверку API-ключа: авторизация выполняется внешней платформой. При необходимости отдельного защищённого запуска задайте `DOCPIPE_API__REQUIRE_API_KEY=true` и `DOCPIPE_API__API_KEY` (от 32 символов). Проверки здоровья доступны без ключа.

Используйте **один процесс Uvicorn и одну реплику на том заданий**: очередь работает в памяти. Завершённые задания и результаты восстанавливаются после перезапуска из Docker volume; прерванные задания получают статус `failed` и требуют повторной отправки. TTL-очистка работает в фоне и при запуске. Удаление volume уничтожит результаты.

```sh
docker compose --env-file .env -f deploy/docker-compose.yml logs -f
docker compose --env-file .env -f deploy/docker-compose.yml down
```

В Docker Compose включена текстовая проверка OCR и экспортированных документов через AITunnel API. Задайте `AITUNNEL_API_KEY` в `.env`; модель выбирается через `DOCPIPE_REVIEW_MODEL`. Само OCR выполняется локально, а текст для проверки отправляется во внешний API. Локальная LLM не используется. Для запуска вне Compose задайте `DOCPIPE_OFFLINE=false`, `DOCPIPE_REVIEW__LLM_ENABLED=true` и `AITUNNEL_API_KEY`; пример CLI-конфигурации — `configs/aitunnel-review.yaml`. При недоступности проверки отчёт отмечает необходимость ручной проверки. Качество OCR зависит от исходного скана; результаты с `review_required=true` нужно проверить.

## Локальный запуск

### Тестовый режим PDF с картинками неразобранных фрагментов

По умолчанию `render.docx_enabled=false`: DOCX не создаётся и его отсутствие
не считается ошибкой. `render.unreadable_as_image=true` включает региональную
замену неразобранного текста картинками исходных фрагментов.

Кроп используется для пустого/повреждённого текстового блока, известной уверенности
OCR ниже `unreadable_min_confidence=0.7`, пустой ячейки с видимыми знаками,
а также текста, который обнаружен в OCR, но потерялся при сборке PDF.
Ячейки обрабатываются по отдельности, остальные ячейки таблицы сохраняют текст.
После замены PDF пересобирается и проверяется снова (не более двух проходов).
Полная страница фоном запрещена. Фрагменты сохраняются в PNG без потерь.

В `image-fallback.json` перечислены причины, координаты, исходный OCR-текст и
картинки заменённых регионов. В таких регионах текст перестаёт выделяться и
искаться; результат помечается как требующий проверки. Низкая уверенность LLM
сама по себе не является основанием для замены. Изображения берутся из исходного
файла; если файл или границы региона недоступны, потеря текста не скрывается.

Для возврата DOCX задайте `DOCPIPE_RENDER__DOCX_ENABLED=true`,
для отключения замены — `DOCPIPE_RENDER__UNREADABLE_AS_IMAGE=false`.

### Визуальная проверка форматирования через LLM

После сборки можно сравнивать изображения исходной страницы и реального экспорта:
`DOCPIPE_REVIEW__VISUAL_ENABLED=true` (при включённом AITunnel и `DOCPIPE_OFFLINE=false`).
В `configs/aitunnel-review.yaml` и Docker Compose эта проверка включена.
Отчёт `review-formatting.json` содержит формат, страницу, предполагаемую область
дефекта, уверенность, проверенные и пропущенные страницы. Замечания требуют
подтверждения человеком; текст и координаты документа автоматически не меняются.

Визуальная LLM-проверка выполняется только для пересобранного PDF.
Если DOCX явно включён, сохраняются обычные проверки его текста, структуры и
размеров страниц. Визуальная проверка DOCX не выполняется. LibreOffice не требуется.

Ограничения: `visual_max_pages=20`, `visual_max_calls=40`,
`visual_timeout_seconds=180`, `visual_max_side=1600`. Их можно задать в секции
`review` YAML либо переменными `DOCPIPE_REVIEW__…`. По умолчанию используется
основная модель, другую vision-модель можно выбрать через `visual_model`.
Источник разворачивается с учётом OCR-коррекции ориентации. Изображения страниц
отправляются в AITunnel только для проверки и не становятся фоном выходного документа.

Рекомендуется Python 3.11. Установите пакет `pip install ".[docling]"`, скачайте модели Docling и русскую модель командой `python scripts/download_russian_recognition.py`. Укажите `DOCLING_ARTIFACTS_PATH` и при необходимости `DOCPIPE_RU_REC_MODEL_DIR`, затем запустите `uvicorn docpipe.api.app:app --host 127.0.0.1 --port 8000 --workers 1`. Полная последовательность подготовки моделей зафиксирована в `Dockerfile`.

В репозитории хранятся исходники сервиса, конфигурация развёртывания, эксплуатационная документация и подготовка моделей. Генерируемые результаты и временные файлы в него не включаются. Локальные `data/`, `models/`, `reports/` игнорируются Git и исключены из Docker-контекста. Лицензии зависимостей перечислены в `LICENSES.md`; шрифты поставляются со своими лицензиями.

## Установка зависимостей

Зависимости пакета определены в `pyproject.toml`; `requirements.txt` подключает
OCR и GLM. Поддерживаемая минимальная версия Python — 3.11.

```sh
python -m pip install -r requirements.txt
python -m pip check
```

Параметры и ограничения развёртывания: [docs/deployment.md](docs/deployment.md).
